RAG 与知识系统

用 ChatGPT、Codex 与 Markdown 搭建个人知识库

从原稿、润色 PDF 到正式 Markdown，记录一套本地优先、可追溯、可持续维护的个人知识工作流

发布于 2026.01.18 更新于 2026.08.12 约 6 分钟

我想建立的，不是一个不断堆积 PDF、网页收藏和聊天记录的资料文件夹，而是一套可以长期维护、随时检索、持续修正的个人知识系统。

最初，我也考虑过向量数据库、知识图谱、自动标签、自动复习和全自动分类。真正开始实践后才发现，第一版最重要的并不是功能多少，而是能否形成一个稳定闭环：知识进得来、找得到、改得动，也能追溯它最初从哪里来。

最后采用的基础组合非常简单：

一、先确定唯一的知识真源

知识系统最常见的问题，是同一内容同时存在于聊天记录、PDF、云笔记和本地文档中，久而久之却没人知道哪一份才是最新版本。

我的选择是：

本地 Markdown 是正式知识的权威版本；ChatGPT 负责润色和辅助理解；Codex 负责理解材料、组织知识和维护文件；脚本只承担确定性任务。

这条原则解决了三个长期困扰我的问题：

  • AI 对话不再承担长期存储职责；
  • PDF 保留阅读体验，但不作为日常检索的唯一入口；
  • 每条正式知识只有一个持续维护的位置。

先确定唯一真源，再考虑检索、自动化和知识图谱。顺序反过来，系统越复杂，重复版本越难治理。

二、ChatGPT、Codex 和脚本如何分工

三者都能参与知识整理，但各自擅长的工作并不相同。

角色 适合完成的任务 不应该承担的任务
ChatGPT 润色、解释概念、检查理解、辅助学习 决定本地目录、维护唯一版本、直接操作 Git
Codex 读取材料、比较版本、检索旧知识、创建和维护文件 在不确定时自动覆盖原始资料
脚本 哈希、索引、格式检查、链接检查和备份 判断两篇知识应该合并还是拆分

最后，我把分工归纳成四行：

文件是否存在、哈希是否一致可以机械判断；一份文档应该拆成几篇、两个观点是否冲突，则必须理解上下文。

三、为什么同时保留三种版本

对于完整知识，我保留三层内容：

人工原始笔记

原稿保留我最初的表达和判断。它可以用来检查 AI 是否改变了原意，也能帮助我回看自己的认知变化。

润色后的 PDF

PDF 更适合阅读和归档，可以保留图片、表格、代码、公式和图文位置。

正式 Markdown

Markdown 用于检索、关联、更新和 Git 版本管理，是日常问答优先读取的知识。

三者不是简单的重复备份，而是分别承担证据、阅读和复用三种职责。正式笔记会记录原稿与 PDF 的路径及 SHA-256，以便及时发现意外覆盖或文件变化。

四、目录结构如何设计

我没有一开始就按所有学科建立复杂分类，而是先按内容所处的生命周期划分：

这里最重要的边界是：

  • Sources 保存来源，不重复维护最终结论；
  • Knowledge 保存能够跨项目、跨教程复用的知识；
  • Learning 保存学习过程和顺序；
  • Projects 与 Problems 保存具体上下文。

五、三种知识入口

输入的成熟度不同，处理方式也不应被强行塞进同一套模板。

入口 1：完整知识

我提供人工原稿和润色后的 PDF，然后只需要说「入库」。Codex 会保存原件、计算哈希、比较差异、检查图片和表格、检索旧知识，并生成正式 Markdown。

如果润色版改变了结论、数字或代码，系统不会静默选择某一版，而是把差异列出来。

入口 2：零散知识

只有一两句话时，我直接说「收录」。尚不足以独立成篇的内容先进入按日记录的 Inbox/Quick，以后再判断是新建、合并、转为问题还是归档。

入口 3：系统学习

当我要持续学习一个主题时，系统会建立专题目录，维护路线、来源、进度、每次学习记录和章节笔记。只有能够脱离具体教程复用的结论，才会进一步提炼到 Knowledge。

六、PDF 入库不能只提取文本

复杂 PDF 中的知识经常藏在表格、架构图、题注和版面关系里。只读取文本层，得到的内容可能顺序错乱，也可能失去关键上下文。

完整检查至少包括：

  • 渲染并查看全部页面；
  • 检查标题层级和阅读顺序；
  • 检查表格、公式、代码和图文对应；
  • 对扫描页使用 OCR，并标记识别风险；
  • 提取真正承载知识的图片；
  • 保留页码和原件定位。

真正承载知识的原始图片会保存到独立资产目录，并由 Markdown 使用相对路径引用；装饰图、Logo、水印和重复背景默认不提取。文档页面本身不能作为配图直接贴入正文。

表格应优先还原为 Markdown 或结构化数据。若版式过于复杂，就保留原始页码和定位信息，人工提炼能够确认的结构与结论，而不是用整页截图代替知识整理。

七、为什么搜索要分层

原稿、临时记录和正式知识的成熟度不同，也不应拥有相同的检索优先级。

日常回答时，优先搜索：

  • Knowledge；
  • Learning；
  • Projects；
  • Problems；
  • Reviews。

只有在查重、整理或追溯来源时，才扩大到 PersonalRaw、原始文档和 Inbox。

这样既保留全部历史，又不会让同一知识的多个阶段在回答中互相干扰。

八、健康检查比“看起来没问题”更可靠

系统会主动检查：

  • Markdown 元数据是否完整；
  • 笔记状态是否合法；
  • 内部链接和目标文件是否存在；
  • 原稿、PDF 及其哈希是否匹配；
  • 零散记录 ID 是否重复；
  • 学习专题结构是否缺失；
  • 索引是否需要更新。

AI 负责理解，脚本负责验收。两者缺一不可。

九、为什么不做无人值守的 Git 推送

原始笔记和 PDF 可能包含尚未检查的个人信息、内网地址或项目配置。自动任务无法完成真正的语义审查，也会降低我对版本变化的感知。

所以 Git 同步保留为手动动作。只有我明确说「同步到 Git」后，Codex 才会检查变更、敏感信息、索引和健康状态，再提交与推送。

这条规则看似降低了自动化程度，实际上显著压缩了错误上传的风险面。

十、这套系统真正解决了什么

完整闭环最终变成：

回头看，搭建过程中最重要的并不是某个脚本或目录，而是以下几条稳定原则：

  • 不要在记录习惯形成前建设复杂平台；
  • 输入形式可以不同，处理原则必须稳定；
  • 原始资料负责追溯，正式知识负责复用；
  • AI 润色不等于个人观点；
  • 同一结论只维护一个规范版本；
  • 自动化必须服从安全、确认和可回滚。

一个真正有用的个人知识库，不是把所有信息都保存下来，而是让值得保留的知识能够被追溯、被找到、被修正，并在下一次工作中重新发挥作用。
