把能力封装成 Skill：Agent Skills 的结构、加载机制与边界

从目录结构、渐进式披露到 Prompt、MCP、RAG 的能力边界，系统理解 Agent Skills

发布于 2026.01.27 更新于 2026.08.12 约 5 分钟

过去，我们习惯用一段 Prompt 告诉 AI「这次要怎么做」。可当同类任务反复出现，提示词会越写越长，参考资料散落各处，脚本也要临时寻找和执行。原本简单的一次性指令，逐渐变成了难以维护的工作流。

Agent Skills 提供了另一种组织方式：把某类任务需要的说明、流程、参考资料和脚本收进一个独立目录，由 Agent 在任务匹配时按需读取。

它不是一段更长的万能提示词，而是一种让能力能够复用、审查和持续维护的工程结构。

一、Agent Skill 是什么

可以把 Skill 理解为交给 Agent 的「任务手册 + 工具箱」。每个 Skill 都应围绕一条清晰的能力边界展开，例如：

  • 检查并整理 PDF；
  • 生成一份符合团队规范的周报；
  • 根据项目规则完成代码审查；
  • 把一批表格转换成固定格式的报告。

核心不是让 Agent 知道更多，而是告诉它在什么情况下，按照什么流程，使用哪些资源完成任务。

Agent Skills 已经形成开放规范。一个 Skill 至少包含 SKILL.md，也可以携带脚本、参考资料、模板和其他静态资源。

正文至少应回答五个问题：

  1. 什么时候使用？
  2. 需要哪些输入？
  3. 按什么顺序执行？
  4. 失败或信息不足时怎么办？
  5. 最终产物如何验证？

  • 复杂能力可以拆成「入口说明」和「按需资源」，更容易维护。

SKILL.md 适合保存导航、步骤、停止条件和质量要求；长篇规范放进 references/；确定性计算和格式转换放进 scripts/；模板与素材放进 assets/。

四、Skill、Prompt、MCP 与 RAG 的边界

这四个概念经常一起出现，却解决着不同层面的问题，也不存在严格的上下级关系。

概念 主要解决的问题 与 Skill 的关系
Prompt 当前这一次任务要做什么 稳定、可复用的部分可以沉淀为 Skill
Skill 一类任务应如何完成 组织流程、资源、约束和验证方法
MCP Agent 如何连接外部工具或数据源 Skill 可以规定何时以及如何使用 MCP 工具
RAG 如何检索模型上下文之外的知识 可以成为 Skill 工作流中的一个步骤

五、什么任务适合做成 Skill

适合封装的任务通常具有以下特征：

  • 会重复出现；
  • 有比较稳定的执行顺序；
  • 需要读取固定规范或模板；
  • 包含脚本、检查或确定性步骤；
  • 产物可以通过明确标准验收。

不适合急着做成 Skill 的情况包括：

  • 只会执行一次的临时任务；
  • 需求边界仍然非常模糊；
  • 每次输入和输出都完全不同；
  • 还没有找到稳定、可复用的工作方法。

如果一个 Skill 同时声称能写代码、做运营、处理合同、制作视频和管理服务器，这通常不是能力强，而是边界已经失控。

六、开发一个 Skill 的基本步骤

步骤 1：先写清楚边界

明确它解决什么问题、不解决什么问题、需要什么输入，以及最终交付什么。

步骤 2：编写触发描述

同时描述「做什么」和「什么时候使用」，避免只堆关键词。

步骤 3：设计执行流程

把有依赖关系的步骤写出顺序，并说明何时读取参考资料、何时运行脚本、何时必须停止并询问用户。

步骤 4：分配资源职责

  • 可重复计算放进 scripts/；
  • 规范和背景材料放进 references/；
  • 模板和静态素材放进 assets/；
  • SKILL.md 只保留执行所需的导航和规则。

步骤 5：验证触发与结果

至少测试正常输入、缺失输入、边界输入、脚本失败和不应触发的任务。

需要注意的是，教学用的词频摘要脚本只能演示目录结构和调用方式，不能代表生产级中文摘要质量。目录结构可以保持稳定，内部算法则应能够独立替换和测试。

八、容易踩的坑

  • 把整个业务知识库复制进 SKILL.md，造成新的重复真源；
  • 只写理想流程，不写失败、冲突和停止条件；
  • 脚本没有输入校验，却允许 Agent 直接修改重要数据；
  • description 过于宽泛，导致几乎所有任务都触发；
  • 只测试「能不能调用」，不检查最终结果是否正确；
  • 下载第三方 Skill 后不审查脚本和权限范围。

Skill 提高的是流程复用与上下文组织能力，并不会自动消除模型的不确定性。重要操作仍然需要权限边界、结果校验和可回滚设计。
