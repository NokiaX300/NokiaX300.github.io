给 RAG 加上 Agent：混合路由与多阶段审查实践

从单问能答、合问漏标准的案例出发，设计共享检索工具、确定性审查管线、可选补搜与业务进度

发布于 2026.10.05 约 6 分钟

在矿山标准问答的实践中，单独问人员定位系统的技术要求，系统通常能给出相关依据。但把问题改成「分别核对建设、通用技术和在用检测标准，再抽检查项做表」，回答就可能遗漏其中一类标准，甚至误称库内没有对应资料。

我检查后发现，目标文件已经入库。问题出在整句查询的召回和精排截断：较强的特征占据候选，其他阶段的标准没有进入最终证据集。

这次改造因此从两件事开始：增强共享检索层，再为复杂问增加可校验的多阶段管线。本文整理方案与案例观察，尚未提供公开的回归数据和时延报告，因而不把这些观察写成量化成功率。

如果你关心条款直查、章节扩展、文件锁定和原文溯源，可以先读 标准文档 RAG：从固定切块到结构化证据供给。

一、先确认失败发生在哪一层

当系统回答「依据不足」时，至少要区分三种情况：

  1. 库中确实没有对应文件或条款；
  2. 文件存在，但候选召回遗漏了它；
  3. 候选存在，经过精排或上下文压缩后被丢弃。

可以先按题名核对库内清单，再检查各子问题的候选集、精排结果和最终证据。否则增加模型调用只会放大原有误判。

人员定位案例中，查询同时含有建设、通用技术、在用检测三个阶段，以及明确的适用对象。它需要分别找证据，再合并结果。进一步判断图纸或说明书是否充分，还需要材料对照和明确的缺失项。

二、混合路由：普通问答和复杂任务分别处理

我采用的方案保留普通 RAG 路径，为复杂问增加审查管线。

路径 适合的问题 执行方式
普通 RAG 单标准、短追问、常规要求或概览 检索、精排、生成，复用已有引用交互
审查管线 多阶段、多标准、对照、检查项表格 拆任务、分路检索、校验、组织证据、生成
可选 Agent 工具环 既定管线仍有证据缺口，需要继续选择工具 在预算内补搜，再回到证据校验

第一版路由可以用规则识别多阶段词、多个标准点名和审查意图，并提供 auto / rag / agent 模式。边界模糊的问法默认走普通路径，再用误路由样本改规则。

路由同样需要评测：误把简单问分到复杂管线会增加成本，误把复杂任务分到普通路径则可能漏答。应分别记录这两类错误，而非只看最终答案。

三、把检索增强做成共享能力

复杂任务首先需要一组可以独立测试的检索工具。

能力 解决的问题
阶段或并列拆问 避免一句话中某个强特征吞掉其他阶段
文件级多样性 避免单份文件占满最终 Top-K
题名兜底 检查目标标准是否在库，并辅助定位文件
适用对象校验 发现「金属非金属」问题误命中「煤矿井下」材料等错配
条款取文 按稳定文件身份与条款号获取正文及来源

阶段拆分后，需要检查子问题是否覆盖原问题。文件多样性可以按文件轮转，但也要保留相关性门槛，不能为了凑齐文件而加入无关证据。

对象校验既可以触发锁定重搜，也应该返回结构化的缺口。题名与对象词只是辅助定位；真实的适用性判断仍需正文、版本及可靠元数据支持。

这些能力应由普通 RAG 与 Agent 共用，减少两套实现逐渐分叉的风险。

四、固定审查骨架，用代码明确执行边界

审查任务的主要步骤往往比较稳定，可以先组织成确定性管线：

拆问、取文、校验、超时与重试都可以是普通函数。模型用于需要语言理解或归纳的步骤，任务状态则由服务维护。相关角色划分可参考 长文档问答多智能体实践。

输出表格建议至少区分：阶段、检查项、支持条款、材料中的对应位置、缺失信息与待人工复核项。只检索到标准条款，还不足以判断用户材料已经满足要求。

五、开放工具环负责补缺口

在实践记录中，DeepAgents 被设计为可选补搜层。对象或阶段校验仍失败时，模型可以继续调用题名列表、标准检索和条款取文工具。复杂任务在关闭完整工具环时，仍能走既定管线。

这意味着第一阶段可以先验证共享工具和固定流程，后续再按任务需要接入开放编排。框架接口与配置需要锁定版本后验证，本文只讨论职责划分。

补搜层应有最大步数、时间与调用预算。每次补搜都应指出要填补哪一个证据缺口；预算耗尽后返回缺失项，而不是把「继续尝试」变成无限循环。

六、进度展示使用业务阶段

用户等待时更需要知道问题被如何处理，而不是阅读原始工具参数。服务可以通过 SSE 推送业务事件：

前端按阶段合并事件，展示拆解、分路检索、对象校验、补搜和生成的状态。原有答案正文、检索依据和结束事件继续使用既有契约，业务进度独立传递。

失败也要有可理解的状态，例如目标文件缺失、对象不匹配或调用超时。执行过程可以帮助排障，但展示了多少步骤，并不能证明答案可靠；最终仍需检查证据与引用。

七、三个案例指向不同的改造目标

案例 原有现象 改造重点
人员定位的建设、通用技术、在用检测合问 部分阶段文件未命中，或混入不同适用对象 三路短查询、对象校验与题名兜底
尾矿库建设、重大变更、闭库分别对应哪一部分 单问能找到的部分，在合问中被截断 并列拆分和文件级多样性
单一人员定位技术要求 原链路已能够回答 保持普通路径，检查延迟和引用是否退化

实践记录中，前两类问题在改造后能够保留更完整的目标文件。这个观察支持继续验证该方向，但尚不能分离拆问、多样性和 Agent 编排各自贡献了多少收益。

因此，回归时应逐项比较：原始基线、只增强检索、固定审查管线，以及开启补搜工具环。这样才能判断哪些新增复杂度值得保留。

八、上线前要守住的检查

  • 子问题覆盖全部阶段，并保留原有适用对象；
  • 正确文件进入候选后，没有被精排与预算再次挤掉；
  • 校验失败能触发有限补搜，或明确报告证据缺口；
  • 检查项与引用一一对应，材料不足时保留待复核状态；
  • 普通问答的延迟、引用和 PDF 定位能够通过回归；
  • 每条路径记录完整任务耗时、工具调用量与失败原因。

我更看重这次改造能否解释一次失败：缺了哪份资料、哪一阶段没召回、哪里发生对象错配，以及下一次补搜是否真正填补了缺口。能够回答这些问题，才有依据判断 Agent 编排的收益和成本。
