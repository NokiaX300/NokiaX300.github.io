PDF 到 RAG 的第一公里：MinerU 部署、后端选择与解析质量评测

从 Pipeline、VLM 后端实测到跨页表格和质量门槛，梳理复杂文档进入 RAG 前的解析工程

发布于 2026.03.22 更新于 2026.08.12 约 7 分钟

许多 RAG 项目把注意力集中在向量模型、检索策略和大模型上，却忽略了链路最前端的文档解析。事实上，如果标题层级、段落顺序、表格或图片在解析阶段已经丢失，后续分块和检索就只能在错误输入上继续优化。

我使用一组包含制度文档、长篇报告、复杂目录、图片、图例和跨页表格的 PDF，对 MinerU 的不同版本与后端进行了比较。本文整理这次部署与实测过程，并给出最终形成的解析质量门槛。

本文中的速度、显存和质量观察来自特定版本、硬件及 10 份测试 PDF，只代表当时的工程记录，不应直接推广到其他环境。安装前请以 MinerU 官方仓库的当前说明为准。

一、文档解析在 RAG 中负责什么

合格的解析入口远不止「PDF 转文本」，还需要尽可能恢复：

  • 标题与正文层级；
  • 阅读顺序；
  • 图片、题注和图例；
  • 表格结构与跨页关系；
  • 公式、代码和脚注；
  • 页码、边界框和原始资产位置。

这些结构决定了后续能否正确分块、生成可靠的检索元数据，并让最终回答回到原始证据。

二、我比较了哪些后端

测试包含四条路径：

后端 定位 主要代价
0.9 Pipeline 历史基线 长文档存在明显文本丢失风险
2.1 Pipeline 传统解析流水线 速度快、资源占用相对较低
2.1 VLM-Transformers 视觉语言模型本地推理 解析慢，适合验证
2.1 VLM-SGLang 独立 VLM 推理服务 速度较好，但显存开销高

Pipeline 组合版面分析、OCR、公式和表格模型；VLM 路线则直接从页面视觉输入理解内容。两者不是简单的「旧方案与新方案」，而是速度、资源消耗与复杂页面完整性之间的不同取舍。

三、不能只比较解析耗时

为了避免只比较一条耗时数字，我选取了 10 份曾经出现解析问题的 PDF，并同时记录以下维度：

  • 单文档耗时；
  • 文本是否丢句、丢段或生成多余字符；
  • 图片和图例召回；
  • 标题与目录层级；
  • 表格、跨页表格和脚注；
  • GPU 显存与部署复杂度。

测试文件 页数 0.9 Pipeline 2.1 Pipeline 2.1 VLM-Transformers 2.1 VLM-SGLang

结合耗时与解析结果，可以得到几条局部结论：

  • 2.1 Pipeline 单任务速度最快，适合作为默认入口；
  • VLM-Transformers 与 VLM-SGLang 的解析效果接近，但前者明显更慢；
  • VLM-SGLang 速度接近 Pipeline，文本完整性更稳定，但占用更多显存；
  • 0.9 Pipeline 在多个长文档中出现大段文字丢失，不宜继续作为主路径。

在该环境中，SGLang 总显存占用约 68 GB：调度进程约 58.3 GB，另外两个 Python 进程分别约占 6.8 GB 与 2.9 GB。这同样只是特定模型、版本和硬件下的观测值。

接口成功返回，只能说明程序没有报错，不能证明文档已经正确解析。

四、解析质量最容易坏在哪里

文本完整性

丢一行日志很容易发现，长报告中间悄悄少了几段却十分隐蔽。除了抽样阅读，还应比较页数、文本长度分布、异常空页和标题连续性。

图片与图例

图片可能被遗漏、跨页拆分或方向翻转，连续图例也可能被误判为附件。即使图片成功提取，也不代表它已经与题注和正文建立了正确关系。

阅读顺序

版面检测框只能告诉我们元素在哪里，并不等于正确的阅读顺序。双栏、侧栏和跨栏标题仍需结合坐标与区域类型重新组织。

PP-DocLayout 等版面模型可以帮助定位标题、正文、表格、图片和公式，但检测结果仍需转换为可靠顺序：

检查项 样本中的具体表现
短句完整性 0.9 Pipeline 与 2.1 Pipeline 在个别制度文档中各出现过丢句
长段完整性 0.9 Pipeline 在《会计政策》《采购管理办法》等长文档中出现过大段缺失
VLM 文本 本次样本中未观察到同类文本丢失，但仍不能跳过抽检
图片 不同后端均有少量漏图，没有观察到方向翻转
图例 同版本后端结果接近，连续图例仍是共性短板
标题层级 所有后端都不完全可靠，需要检查父子层级和正文归属

版面模型通常返回 chart、chart_title、text、paragraph_title、formula、table、table_title 等区域及其置信度。实验页面中图表、正文和表格区域置信度较高，部分公式区域只有约 0.50–0.80；即使检测框正确，也仍需依据坐标、跨栏规则和区域类型重建阅读顺序。

五、跨页表格：合并成功不等于内容正确

处理跨页表格时，系统通常会先判断：

  • 前一页末块和后一页首块是否都是表格；
  • 宽度和列结构是否接近；
  • 后页是否重复表头；
  • caption 与 footnote 是否允许合并。

满足条件后，再在结构化 JSON 或 HTML 层追加数据行，而不是直接拼接两张原始图片。

即使合并动作完成，仍可能出现：

  • 后页开头没有被识别成表格；
  • 前页末尾缺少内容；
  • 重复表头未正确删除；
  • 图例、题注或脚注归属错误；
  • 列结构相同，但两张表实际上不是同一张表。

所以，跨页表格的验收不能停在「是否成功合并」，还必须同时检查结构与语义。

测试情况 结果 暴露的问题
后页首块被识别为非表格 合并失败 合并条件未被触发
前页末块解析不完整 结构合并成功 合并后的内容仍有漏项
连续三页以上同结构表格 可以连续合并 仍需检查重复表头、脚注和题注归属

六、VLM 与 OCR 更适合做补充路径

复杂页面可以引入 VLM 或专用 OCR 作为补充识别器。以 DeepSeek-OCR 实验为例，判断结果不能只看是否输出了字符，还要继续检查标题层级、段落顺序、表格和公式。

更稳妥的方案是分级路由：

补充识别器的结果也应转换为结构化检查项，而不是只保存页面截图。例如：

字段 检查含义
has_title 标题是否识别且与文件主题一致
has_content 正文主体是否存在，是否发生大段缺失
signature_complete 签章、日期等关键区域是否完整
reading_order_ok 多栏、表格和非线性版面的顺序是否合理

生产环境使用 VLM 时，我更倾向于让推理引擎作为独立服务运行，解析进程通过接口访问。不要在每个 Web 工作线程中重复初始化大模型。

七、为解析器建立统一适配层

后续知识入库不应直接依赖某一种解析器的私有输出。更稳妥的做法，是先转换为统一结构：

有了统一适配层，系统就可以替换解析器、增加 fallback，也能对不同结果进行差异评测。

八、进入知识库前的质量门槛

  • 页数与原文件一致；
  • 没有异常空页或大段文本骤降；
  • 标题层级和阅读顺序合理；
  • 图片、题注和正文能够对应；
  • 表格行列、跨页合并和脚注完整；
  • 公式、数值和单位得到保留；
  • 每个块都能回到文件、页码和资产；
  • 关键文档完成抽样或双路检查；
  • 内网地址、密码和个人信息已经处理。

最终 Markdown、结构化 JSON、提取资产与原始 PDF 应保持可追溯关系。

九、我的选型结论

对普通文档，我会先使用资源成本较低的 Pipeline；遇到长篇法规、关键报告、复杂表格或未通过质量检查的页面，再切换到 VLM 或其他解析器。真正值得投入的，不是追逐单一最强模型，而是建立稳定的质量检查、降级与回溯能力。
