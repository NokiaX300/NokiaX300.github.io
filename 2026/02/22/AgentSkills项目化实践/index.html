把 Agent 做成工程：从 Spec、Ticket、TDD 到可验证交付

用规则、规格、测试、Provider 隔离和确定性裁决，把模糊想法推进为可交付的 Agent 系统

发布于 2026.02.22 更新于 2026.08.12 约 5 分钟

上一篇介绍了 Agent Skills 的结构、渐进式披露和能力边界。可当 Agent 真正进入项目，问题很快就会从「如何写一个 Skill」升级为：

  • 模糊需求怎样变成可验收规格？
  • Agent 生成的建议能否直接修改业务状态？
  • 多个 Agent 发生冲突时由谁裁决？
  • 外部模型不可用时，测试和核心流程还能不能运行？
  • 下一位开发者或 Agent 如何接着工作？

这些问题无法靠一段更长的 Prompt 解决。要让 Agent 从演示走向交付，软件工程必须进入系统设计。

一、Agent 不是一个模型，而是一套反馈系统

模型主要负责其中的推理与表达。真正决定系统是否可靠的，是上下文是否权威、工具权限是否受控、输出是否经过校验，以及失败后能否恢复。

让 LLM 提出意图和解释理由，让确定性规则修改权威状态。

ActionProposal 只是想做什么；通过校验和裁决后才能变成 Action；确定性执行产生 StateTransition，最终再记录为可审计的 WorldEvent。

二、不同规则载体各自负责什么

项目里经常同时存在 AGENTS.md、Rules、Skills 和 Prompt。若职责没有划清，它们很容易复制出多套彼此冲突的规则。

载体 主要职责 不适合承载
AGENTS.md 项目背景、架构原则、协作入口、权威资料位置 临时需求和完整业务规则表
Rules 长期编码规范、测试要求和禁止事项 一次性任务步骤
Skill 可复用工作流、读取顺序、停止条件和验证方法 复制整份 Spec 或领域规则
Prompt 当前目标、范围、验收标准和临时限制 长期稳定约束

项目只能有一套权威业务规则。Skill 应引用它，而不是复制它。

三、从模糊想法到可验收 Spec

一条相对稳定的路线是：

统一资料位置

先明确产品文档、领域规则、ADR、Spec 和 Tickets 的权威目录，同时统一 ready、in_progress、resolved 等状态含义。

只追问高杠杆问题

不要试图一次问完全部需求。只询问会阻塞当前功能切片的问题，并把稳定结论写回仓库，而不是留在聊天记录里。

先统一领域词汇

明确对象的所有权、生命周期、状态转换和失败场景。没有领域边界的抽象，只会制造更多名字。

把验收标准写成测试入口

每项验收标准都应该能够落到一个明确测试；「性能良好」「体验友好」「支持异常情况」都不是可执行标准。

四、Ticket 应按用户价值纵向切分

如果把任务横向拆成「先写所有模型、再写所有 API、最后做界面」，系统会长期处于无法演示的状态，集成问题也会被推迟到最后。

一个 Ticket 完成后，应该形成能够独立验收的小闭环，而不只是完成了某一层的代码。

五、让 Agent 真正执行小步 TDD

Agent 很容易一次修改许多文件，再补上一批看似合理的测试。要获得可信反馈，仍然要坚持小步 RED-GREEN：

  1. 为一个公开行为编写失败测试；
  2. 运行测试并确认它因预期原因失败；
  3. 只实现让当前测试通过的最小代码；
  4. 运行相关测试和回归测试；
  5. 再进入下一个行为。

resolved 不等于「代码已经写完」，而是验收标准、测试、构建结果和必要文档都有证据支撑。

六、用 Provider 隔离真实模型

如果领域逻辑直接依赖某个在线模型，自动化测试就会受到网络、费用、输出波动和限流的共同影响。

可以先定义统一协议：

领域 Agent 与 Provider 不应揉进同一个类。通过统一接口，我们可以稳定覆盖：

  • 正常结构化输出；
  • 非法字段和未知枚举值；
  • 超时、异常和限流；
  • 降级路径；
  • 恶意输出是否能越权修改状态。

Agent 获得的上下文也应是只读快照或深拷贝，而不是可直接修改共享状态的引用。

七、Prototype 的目标是发现错误，不是提前写生产代码

不同未知问题需要不同工具：

  • research：确认 SDK、协议、框架能力等外部事实；
  • prototype：验证字段、状态和规则组合是否可行；
  • wayfinder：处理多个相互依赖、路径尚不清楚的未知问题。

原型最有价值的产物不是代码量，而是经过验证的发现。例如，多条资源规则单独看都合理，组合后却可能让某个行动永远无法触发。

有效结论应进入 Spec、ADR 或领域文档；原型代码默认可丢弃，生产实现不应偷偷依赖它。

八、多 Agent 的重点是隔离与确定性裁决

增加 Agent 数量不会自动提高质量。协作式架构最容易遭遇共享状态污染、部分失败和结果冲突。

关键规则包括：

  • 每个 Agent 读取同一份周期快照；
  • 不读取其他 Agent 本周期的提议和失败原因；
  • 单个 Provider 失败不拖垮整个周期；
  • 政策互斥与资源竞争分开处理；
  • 使用固定优先级和稳定排序；
  • 随机 ID、时间和返回顺序不能改变裁决结果；
  • REJECTED 与 FAILED 必须分开记录。

最终只有通过裁决的 Action 才能修改状态，并生成连续、可回放的事件记录。

九、维护和交接同样属于交付物

成熟项目不应该依赖旧聊天才能继续。一次可用的交接至少需要说明：

  • 项目怎样启动和验证；
  • 权威文档在哪里；
  • 当前 Ticket 和完成状态；
  • 已知限制与失败场景；
  • 下一项建议工作；
  • 哪些操作需要人工确认。

十、一个可靠 Agent 项目的检查清单

  • 权威资料和规则只有一套；
  • Spec 包含目标、非目标、错误和可执行验收标准；
  • Ticket 按用户价值纵向切分；
  • Agent 只能读取状态快照；
  • 模型输出经过结构和领域校验；
  • 核心测试不依赖真实外部模型；
  • 多 Agent 冲突由确定性规则裁决；
  • 超时和部分失败不会留下半状态；
  • Timeline 记录事实，Replay 可以恢复；
  • Handoff 允许新 Agent 脱离旧聊天继续工作。

Agent 工程真正要解决的，不是如何让模型更自由地行动，而是如何让每一次行动都有清晰边界、验证证据和可恢复的结果。
