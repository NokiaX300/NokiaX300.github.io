RAG 与知识系统

长文档问答的正确拆法：解析、检索、多 Agent 推理与校验

将长文档问答拆成可观测、可评测、可回溯的分层工作流，并讨论什么时候真正需要多 Agent

发布于 2026.06.14 更新于 2026.08.12 约 5 分钟

随着模型上下文不断变长，一个很自然的想法是：把整份文档直接塞进去，让模型自己寻找答案。

这种方式在小规模演示中很方便；可当文档继续变长、问题需要跨段综合，或证据必须精确定位时，位置敏感、内容遗漏、成本过高和难以排错等问题依然会出现。

我的长文档问答方案采用分层架构：

多 Agent 只是其中一种编排方式。它的目标不是增加角色数量，而是让每个阶段都有清晰的输入、输出和失败边界。

一、为什么长上下文不等于可靠问答

直接输入长文档仍可能遇到：

  • 关键信息位于中间位置时被忽略；
  • 不同章节存在相似表述，模型引用错误版本；
  • 表格、图片和页码在纯文本中丢失；
  • 跨章节问题需要先找证据再建立关系；
  • 回答正确，却无法给出可靠引用；
  • 出错后无法判断是检索失败还是推理失败。

因此，长上下文更适合作为一项可选能力，而不是解析、检索和证据管理的替代品。

二、五层架构

解析层

读取 PDF、Word 等原件，恢复标题、段落、表格和原始图片，同时保留页码与资产位置。

组织层

根据语义与标题分块，建立章节摘要、文档摘要和父子结构。每个 Chunk 都必须能够回到原页。

检索层

组合关键词、向量、元数据过滤和必要的图检索。复杂问题可以先拆成子问题，再分别检索。

推理层

基于已经召回的证据进行比较、归纳或多步推理，不把模型记忆当作事实来源。

校验层

检查事实是否有证据、引用是否准确、多个结论是否冲突，再决定是否需要重新检索。

三、一个多 Agent 时序

这条时序可以归纳为五个关键动作：

  1. 用户问题与压缩后的对话记忆一起进入规划环节；
  2. Planner 分析问题类型并拆分搜索任务；
  3. 查询改写后执行多路检索，返回带来源的候选证据；
  4. Researcher 跨来源整合、推理并处理证据冲突；
  5. Synthesizer 生成带引用的草稿，Verifier 通过后再更新记忆并返回用户。

可以把角色拆成：

角色 输入 输出
Planner 用户问题、文档清单 子问题与执行计划
Retriever 子问题、索引 带来源的候选证据
Researcher 证据与上下文 局部分析结果
Synthesizer 多个局部结果 结构化答案草稿
Verifier 草稿、证据集合 通过、驳回或补检索要求

并不是每个角色都必须对应一个独立的大模型实例。确定性预处理、过滤和格式校验，仍应由普通代码完成。

结构化 metadata 让我们能够追踪页码、块号、来源和失败状态。缺少这些字段，多 Agent 就只是在互相转发无法审计的聊天内容。

五、会话记忆、长期知识和任务状态要分开

三种状态承担不同职责：

  • Session Memory：当前对话中的上下文、用户追问和临时选择；
  • Knowledge Base：经过维护、可跨会话复用的长期事实；
  • Task State：计划、步骤状态、中间产物、重试次数和错误。

把它们混进同一份 Memory，既会让临时推测污染长期知识，也会使过期信息难以治理。

记忆不是保存得越多越好，而是每一类信息都有清晰生命周期。

六、工具调用必须可观测

检索、网页搜索、解析器和代码工具都需要：

  • 明确输入输出 Schema；
  • 超时与有限重试；
  • 调用日志与耗时；
  • 结果结构校验；
  • 失败后的降级路径；
  • 来源和版本记录。

并行只用于互不依赖的步骤。需要前一步结果才能决定下一步查询时，应保持顺序执行。

AgentScope 等框架可以提供消息、Memory、Tool、Pipeline、并发、路由和 Handoff 等抽象，但不会替项目自动划定正确的角色边界。

七、Verifier 不应该只是再问一次模型

如果 Verifier 只收到答案，再被笼统地问一句「这段答案对吗」，它很可能只是重复前一个模型的错误。

更有效的校验包括：

  1. 每个结论是否绑定证据 ID；
  2. 引用内容是否真的支持该结论；
  3. 数字、时间、主体和单位是否一致；
  4. 多个来源之间是否冲突；
  5. 是否存在关键子问题未回答；
  6. 证据不足时是否明确拒绝推断。

八、怎样评测长文档问答

最终答案指标包括：

  • 事实正确性；
  • 证据完整性；
  • 引用准确性；
  • 跨段和跨文档综合能力；
  • 对信息位置变化的鲁棒性；
  • 延迟、Token 和工具调用成本。

除了最终答案，还应记录各阶段指标：

  • 解析是否遗漏内容；
  • 相关证据是否进入候选集；
  • Reranker 是否把正确证据排到前面；
  • 推理是否错误使用了正确证据；
  • 校验器是否发现错误；
  • 重新检索是否真正改善结果。

九、什么时候不需要多 Agent

以下任务通常使用固定 Workflow 或单 Agent 更合适：

  • 步骤稳定、分支很少；
  • 单次检索即可回答；
  • 延迟和成本要求严格；
  • 角色拆分后没有独立可验证产物；
  • 多个 Agent 只是重复阅读同一上下文。

多 Agent 真正有价值的场景包括：

  • 子任务可以独立检索或并行分析；
  • 不同角色使用不同工具或知识边界；
  • 需要明确的互验和冲突处理；
  • 每个中间产物都可以保存和评测。

十、落地检查清单

  • 原始文档、Chunk、图片和页码可以互相追溯；
  • Planner 的子问题覆盖原始问题；
  • 消息使用稳定 Schema，而不是自由文本接力；
  • Session、Knowledge 与 Task State 分离；
  • 工具具备超时、重试、日志和校验；
  • Verifier 能触发补检索和冲突处理；
  • 每个阶段都有独立指标与失败分类；
  • 使用多 Agent 的收益高于额外成本。
