中文 RAG 检索怎么选：Embedding、Reranker 与 Qdrant

从业务黄金集到向量库参数，建立一套可复现的中文 RAG 检索评测与上线流程

发布于 2026.04.19 更新于 2026.10.05 约 7 分钟

搭建 RAG 时，最容易的做法是从榜单上挑一个 Embedding 模型，再把向量写进数据库。真正困难的问题是：面对我的中文文档、真实问法和过滤条件，它是否真的比另一个模型更好？

我早期的 RAG 管线依次经历了 PDF 解析、Markdown 清洗、分块、Embedding、Qdrant 入库、检索和生成。经过多轮测试，我把模型选择与向量库配置整理成了一条可复现的评测流程。

一、检索质量从文档解析开始

一个完整链路是：

如果解析已经丢段、阅读顺序错误，或者分块没有标题和页码，再强的向量模型也无法恢复原始信息。

Embedding 决定“哪些内容看起来相关”，Payload 决定“结果能否被过滤和追溯”。

二、不要先选模型，先做业务黄金集

公开榜单适合缩小候选范围，却不能代替本地评测。一个小型业务黄金集至少应包含：

  • 用户真实可能提出的中文问题；
  • 每个问题对应的相关文档和 Chunk；
  • 同义表达、口语化表达和缩写；
  • 容易混淆但不相关的困难负样本；
  • 需要元数据过滤的问题；
  • 没有答案的问题。

第一版不必盲目追求规模。几十到几百个经过人工确认的问题，通常比数千条自动生成却未经核验的数据更有价值。

需要固定并记录：

  • 原始文档版本；
  • 分块策略与 Chunk 大小；
  • 模型名称和版本；
  • 向量维度与归一化方式；
  • 查询模板；
  • 数据库参数和评测代码版本。

三、Embedding 模型应该比较什么

中文语义能力只是起点，还要同时考虑：

维度 需要回答的问题
检索质量 相关内容能否进入 Top-K
向量维度 存储、内存和计算成本是否可接受
上下文长度 长 Chunk 是否会被截断
吞吐与延迟 入库和在线查询是否满足目标
部署资源 CPU/GPU、显存和并发要求
许可证 是否允许目标部署方式

在这组结果中，Qwen3-Embedding-0.6B 的 nDCG 指标整体领先，Qwen3-Embedding-4B 的 MAP 指标更高。但多个模型的 MAP@1 与 MRR 都达到 1.0，也说明样本规模和区分度仍然有限。最终选择仍需结合延迟、显存、向量维度和实际 Top-K 召回来判断。

常用指标包括：

  • Recall@K：相关结果是否进入前 K 个；
  • MRR：第一个相关结果出现得有多靠前；
  • nDCG@K：多个相关结果的排序质量；
  • P50/P95 延迟：典型与尾部响应时间；
  • 吞吐、显存和向量存储体积。

不同模型的相似度分数尺度不一定相同，不能拿一个模型的 0.75 与另一个模型的 0.75 直接比较。

四、什么时候需要 Reranker

Embedding 负责从大量 Chunk 中快速召回候选，Reranker 再对较小的候选集进行更细致的相关性排序。

适合增加 Reranker 的情况：

  • 召回率不错，但前几名排序不稳定；
  • 文档中有大量相似条款或模板化段落；
  • 查询与答案需要更细粒度匹配；
  • 允许增加一定在线延迟。

如果正确内容根本没有被 Embedding 召回，Reranker 也无法凭空找回。因此，应先确认 Recall@K，再决定是否继续优化排序。

对于标准、制度和会议纪要，还要检查结构性失败：条款是否被切碎、概览是否漏掉同章内容、点名文件或年份时是否串到其他材料。这些问题需要条款直查、结构扩展或文件约束，可以继续阅读 标准文档 RAG：从固定切块到结构化证据供给。

五、Qdrant 集合设计

创建 Collection 前必须固定向量维度和距离度量。Payload 则只保存检索、过滤和追溯真正需要的字段：

大对象、原始图片和完整文件不应直接塞进 Payload，只保存稳定引用。经常参与过滤的字段应建立 Payload Index，并尽量在大批量数据进入前设计好。

六、HNSW 参数怎样影响检索

参数 增大后的典型效果 主要代价
m 图连接更丰富，召回可能提高 内存和索引体积增加
ef_construct 建图搜索更充分 建库时间增加
查询 hnsw_ef 查询候选更多，召回可能提高 查询延迟增加

这些参数不存在适用于所有数据的最佳值。真实数据量、向量维度、过滤比例和并发模式，都会改变召回与延迟的平衡。

对于很小的集合，暴力搜索可能已经足够；当集合增长后，再比较 HNSW 的召回与延迟收益。

七、量化不是免费的压缩

量化可以减少内存或提高搜索速度，但会引入近似误差。

  • 标量量化通常是较稳妥的起点；
  • 二值量化压缩更强，对数据分布与模型更敏感；
  • 应开启或比较原始向量重打分；
  • 评测必须同时记录召回、延迟、内存和磁盘。

不要只因为数据能够放进内存，就认为量化配置已经成功。量化前后应使用同一黄金集对比，并特别观察困难查询是否率先退化。

八、一次完整的对比实验

固定输入

锁定文档、分块、问题集和判定标准。

建立纯向量基线

分别测试候选 Embedding，记录 Recall@K、MRR、nDCG 和延迟。

增加过滤场景

测试文档类型、版本、权限、日期等真实过滤条件，并检查 Payload Index。

增加 Reranker

比较排序改善与额外延迟，不默认认为加入后一定更好。

压测索引参数与量化

同时记录建库时间、内存、磁盘、P95 延迟和召回变化。

做失败样本分析

把失败分成解析错误、分块错误、未召回、排序错误、过滤错误和生成错误，避免所有问题都归因于 Embedding。

九、模型升级必须按数据迁移处理

更换 Embedding 模型后，即使向量维度相同，语义空间也已经改变，旧向量与新查询向量不能混用。

更安全的流程是：

不要在原 Collection 中悄悄混写两个模型生成的向量，否则问题往往会以难以解释的召回波动出现。

十、我的最终原则

  • 榜单只用于生成候选，不用于直接做结论；
  • 先建立业务黄金集，再讨论模型和参数；
  • 先看召回，再看排序，最后看生成；
  • Payload 必须让每个结果回到原始证据；
  • HNSW、量化和并发参数都用真实数据压测；
  • 任何模型升级都要有新索引和回滚方案。
